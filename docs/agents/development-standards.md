# 开发与测试约束

本文档适用于整个仓库的业务代码、UT、integration test 和 E2E，也是代码评审的必查项。

## 稳定场景 ID

- 已有稳定场景 ID 是历史追踪身份，不重命名；其兼容清单冻结在 `test/testenv/testdata/legacy-acceptance-ids.txt`，后续不得追加旧格式 ID。
- 新增稳定场景 ID 必须由其 GitHub Issue 独占分配，不再读取仓库中的最大编号。格式分别为 `UT-<DOMAIN>-GH<ISSUE>-<SEQ>`、`IT-<DOMAIN>-GH<ISSUE>-<SEQ>`、`HELM-GH<ISSUE>-<SEQ>` 和 `E2E-<KUBERNETES_MINOR>-<DOMAIN>-GH<ISSUE>-<SEQ>`。
- `<ISSUE>` 是实现该场景的 GitHub Issue 编号，不补零；`<SEQ>` 在同一测试层级、目标版本、领域和 Issue 内从 `001` 独立递增。例如 Issue #53 使用 `UT-KSM-GH53-001` 和 `E2E-119-KSM-GH53-001`。
- 验收矩阵的来源必须包含 ID 中对应的 `#<ISSUE>`。不得使用 UUID、时间戳、全局自增序号或合并时重编号代替该规则。

## E2E

- 实现任何 Issue/ticket 前先完成 `docs/agents/issue-tracker.md` 的「实现前 E2E 评论」步骤；发布并回读相关 case 后才开始修改业务代码或测试。
- 验收矩阵中每个 E2E case 必须分别填写「验收目的」「执行步骤」「执行预期」三列，且内容不能为空。验收目的说明要证明的能力或约束；执行步骤按顺序说明准备输入、执行动作和观察结果；执行预期给出可判定通过或失败的具体状态、指标或不变量，并与测试源码一致。多个目标版本共用一行时，必须明确其执行步骤或预期的版本差异。
- 所有 E2E 场景和业务断言必须使用 Go 的 Ginkgo/Gomega 编写。
- shell 和 Makefile 只负责环境编排，例如工具准备、kind 集群生命周期、镜像构建与加载、Helm 安装和失败 evidence 采集；不在 shell 中实现或复制 E2E 业务断言。
- 异步状态使用有明确超时上限的 `Eventually` 或 `Consistently`，不使用固定长时间 `sleep`。
- 每个 blocking E2E 场景在 `Describe`/`Context`/`It` 或 label 中保留稳定场景 ID，并在 CI 中产生可追溯的 JUnit 结果。

## 中文意图注释

- 对不能仅通过命名直接读懂、且承担独立阶段的连续逻辑，在代码段之前写明确的中文意图注释，说明接下来一段要完成什么。
- 一个函数或测试场景包含多个阶段时，分别标明准备输入、执行动作、等待收敛、验证不变量和清理资源等阶段；Ginkgo 场景优先使用中文 `By(...)` 表达这些步骤。
- 注释解释意图、业务约束或“为什么”，不逐行翻译语法；短小且通过命名已能完整表意的代码不增加噪声注释。
- 代码行为、阶段边界或不变量改变时，同步更新相应注释。

## 评审完成条件

代码评审必须确认：

1. 没有用 shell 替代 Ginkgo E2E 业务场景或断言。
2. 非平凡的大段代码和 UT/E2E 的阶段边界都有准确的中文意图注释或中文 `By(...)`。
3. 注释与实际行为一致，且没有用无信息量的注释掩盖过长或过于复杂的代码。
4. 验收矩阵中每个 E2E case 都具备非空的验收目的、执行步骤、执行预期，且与实际测试一致。
5. Issue 的实现前 E2E 评论已发布并回读；实际实现、测试与验收矩阵覆盖该计划，范围变化已同步到评论。
